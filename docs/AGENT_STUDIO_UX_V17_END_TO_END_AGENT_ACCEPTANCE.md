# Agent Studio V17｜从真实用户操作出发的 Agent 完整闭环验收

> 对象：独立的 `agent_studio_vibex版本`，**仅桌面 Web**。任务目标：从空白需求输入创建「需求落地全链路 Agent」，验证模型生成、资源配置、MCP、知识库、人工审批、最终交付、评估、反馈、方案优化和再次试跑。
>
> **验收范围边界**：隔离临时 PocketBase + 实际 Chrome 浏览器 + 本地模拟模型服务 + 真实 HTTP MCP JSON-RPC 请求。隔离账号和数据在测试后清理；**不代表该 Agent 已出现在生产或公司内网数据库，也不代表使用了真实付费模型/真实第三方 OAuth**。

## 1. 测试 Agent 的实际功能设计

- 角色：需求落地规划助手。
- 输入：原始自然语言需求，以及员工主动授权的规范资料。
- 第一次工作阶段：澄清目标、范围、非目标、资源、风险、优先级和可验证完成标准。
- 人工关卡：把结构化需求方案送到员工面前，必须由员工批准或退回修改。
- 第二次工作阶段：在已批准的需求范围内拆解实施步骤、里程碑、负责人建议、风险与验收清单。
- 工具：平台内置 `knowledge_search`、`calculate` 和由员工明确选择的 `mkt__<connection-id>__doc_search`。`doc_write` 未授权、不调用。
- 审计：所有工具调用、人工审批、输出和反馈保留运行 ID、服务器事件、AgentSpec 版本快照。

同样的方案结构已作为 **「需求落地规划助手」** 增加到 `src/pages/Home/presets.ts`；员工可从工作台「从模板开始」加载，再接入**自己**的模型、知识库和插件。模板没有任何私人连接 ID、凭据或固定用户数据。

## 2. 本轮完整桌面 Chrome 用户操作证据

| 阶段 | 员工在浏览器中的操作 | 核验结果 |
|---|---|---|
| 01 输入需求 | 在空白五步创建向导填写 `V17_CREATE_JOURNEY` 需求，点击生成 | 模拟模型服务通过真实 HTTP 收到生成请求，创建出正式可编辑 AgentSpec |
| 02 审阅方案 | 检查方案目标、交付物、任务步骤、`require_plan_review` | 人工关卡参数为 true，工具别名归一化到真正可执行 ID |
| 03 MCP 工具 | 选择已探测的 `doc_search`，保存 Agent | 服务器正式方案包含带连接 ID 的 MCP 工具，**不包含**不可执行别名和 `doc_write` |
| 04 知识库 | 创建知识库、粘贴规范资料并索引、返回创建向导勾选关联库 | 资料真实保存并可检索，返回创建页同步最新库权限后放行资源检查 |
| 05 启动试跑 | 选择员工自己的模拟模型，填写实施任务指令并启动 | 真实 `agent_runs` 记录产生，含源 AgentSpec 快照、模型与工具清单 |
| 06 多工具执行 | 内置知识库检索和计算器；调用经授权 MCP `tools/call` | 三种工具都产生 `tool_result` 事件，每次调用有服务器记录 |
| 07 工具审批 | 出现 MCP 调用审批卡，员工点击批准 | MCP 真实 HTTP 调用只在批准后出现；首次批准前调用次数为零 |
| 08 草案审批 | 出现结构化需求方案人工确认，员工批准 | `awaiting_input` 与 `input_received` 可核验，继续生成最终实施计划 |
| 09 第一次交付 | 查看包含阶段、负责人、验收标准的 Markdown 成果 | 运行状态 `succeeded`，结果与运行事件保存 |
| 10 评估反馈 | 点击生成评估、填写负反馈并提交 | 评估和反馈分别持久化到该次 Run |
| 11 方案优化 | 依据真实评估与反馈生成方案 diff，人工确认写回 | 正式 Agent 目标版本更新、MCP/知识库绑定仍保留，旧 Run 快照保持不变 |
| 12 再次试跑 | 点击「再次试跑改进版」，确认并编辑预填指令，再启动 | 点击“准备试跑”本身不调用模型；第二个 Run 使用新 AgentSpec 快照 |
| 13 第二次完成 | 再次人工审批 MCP 调用与需求方案，查看最终交付并生成评估 | 第二个 Run `succeeded`、再次产生 3 条工具结果；第二次评估独立落库 |
| 14 插件市场操作 | 独立浏览器场景打开插件市场 → 自建 MCP → 输入 URL → 验证并连接 → 回 Agent 资源选择 | 真实 `tools/list` 发现 2 个工具，只有员工勾选的 `doc_search` 被写入 Agent，敏感 `doc_write` 未授权 |

### 关键计数（隔离测试）

- Agent 生成模型请求：1 次。
- 计划执行模型请求：10 次（两轮合计）。
- MCP `tools/call`：2 次，均已审批。
- 两次完整 Agent 运行：2/2 成功。
- 工具结果事件：每次 3 条，共 6 条。
- 人工需求方案审批：2 次。
- 两轮运行均有结果与评估；第一轮负反馈驱动下一版本，第二轮使用更新的配置。

## 3. 从真实使用失败中修复的产品问题

| 优先级 | 发现问题 | 修复 | 保护边界 |
|---|---|---|---|
| P0 | AI 生成人类可读 `doc_search`，用户选择 MCP 连接后通用别名还保留为“待连接”，导致阻断试跑 | `chooseVerifiedAgentTool` 选择 MCP 时清理同名非执行别名；工具匹配器不会把未明确选择的外部写工具伪装成已授权 | 授权仍由员工选择，连接的确切 ID 归员工 |
| P0 | 资源第三步的知识库列表只在初次加载时读取，创建库后返回无法勾选 | `useHome` 增加知识库刷新/错误/加载状态，向导切入资源步重新同步，资源区提供刷新按钮 | 权限以服务器当前账号结果为准；读取失败不伪装成空库 |
| P0 | 本次试跑关闭通用写审批时，市场 MCP 工具竟会在无人工确认下调用 | 共享 `tool_policy.js` 将任何市场 MCP 工具设为**逐次审批**，通过后的单次调用才可执行；HTTP 工具的可选规则保持独立 | 测试确认先审批后调用，不能把一次批准变成永久授权 |
| P1 | 审批卡把 MCP 只读查询描述成“写操作” | 根据具体工具类型显示「市场插件调用，需要确认」与单次授权解释 | 不把 MCP 元数据当作绝对只读保证 |
| P1 | 优化成功后只能翻回页面顶部手动开始新运行，反馈和下一轮验证仍割裂 | 优化成功区域新增「再次试跑改进版」，预填原任务、正确选择新 AgentSpec、清除旧 Run URL；**不自动启动付费模型** | 旧运行结果与反馈保持在历史中 |
| P1 | 完整示例只存在隔离测试数据，员工无法快速复用 | 添加「需求落地规划助手」内置模板，要求人工确认，默认仅包含可执行内置工具；可后接用户自己的 MCP | 不植入任何插件身份、知识库或私人凭据 |
| P1 | 自建 MCP 验证连接后只清空表单，没有明确下一步 | 插件市场返回成功的工具数与操作提示；如果二次探测失败如实指出，不宣称已经可用 | 仅成功探测才显示“真实发现 N 个工具” |

## 4. 复现实验命令与最终结果

所有测试运行于隔离环境，不连接真实用户数据库。

- 浏览器完整创建与两次交付：设置环境变量 `AGENT_STUDIO_UX_FULL_CREATION_ONLY=1` 后运行 `node --test tests/agent-review.chrome.mjs` → **1/1 PASS**。
- 浏览器自建 MCP 插件连接与授权：`AGENT_STUDIO_UX_CONNECT_UI_ONLY=1` + 同一测试文件 → **1/1 PASS**。
- 工具匹配、审批规则、内置模板：`node --experimental-strip-types --test tests/agent-delivery-preset.test.mjs tests/agent-tool-matcher.test.mjs tests/tool-policy.test.mjs` → **16/16 PASS**。
- `pnpm build` → **PASS**，包括 TypeScript、Vite 构建和独立 PG pilot 的静态资源隔离验证。
- `pnpm test:e2e:parallel` → **20/20 PASS**，2 个并行 Worker，125.4 秒；覆盖知识库、MCP、执行、调度、权限和协作等主链路。
- 未执行生产网络发布、数据库切换或 GitHub 推送。源代码工作树仍含其他并行迁移改动。

## 5. 尚待真实公司环境验收，不得夸大

1. **真实外部供应商**：测试 MCP 服务由本地临时 HTTP 服务提供，模型是稳定可控模拟；尚未验证实际第三方 OAuth、配额、费率、外网代理和失败重连。
2. **真实需求方案质量**：本次模型刻意输出确定性方案，测试证明执行和人工关卡真实生效，不证明生成的计划在实际项目中更准确，也不能以两次评分都能保存推断质量提升。
3. **内部真实持续部署**：本轮测试 Agent/知识库是临时账号的隔离数据，测试退出后清理；内置模板随前端代码发布才会在正式网页中出现。并未操作用户内网生产数据库。
4. **真实人工团队及复杂文档**：多人并发的运营审批、复杂 OCR/PDF、海量项目数据、长期 Worker 7×24 运行和断网恢复，仍需在真实环境中分别验收。
5. **PG 迁移**：仅保留 PostgreSQL staging 实验任务，不涉及正式切换。维持 GO/NO-GO 和备份/迁移对账要求。

## 6. 下一轮桌面 UX 建议

优先在 Agent 运行历史中提供**前后版本评估对比**（要区分模型主观分和规则分）、工具调用费用/耗时归因、可追溯的“因哪条反馈而更新了哪些配置”的版本记录；随后进行真实员工试用、超时/限额/断网回归和工具撤权后的恢复引导。
