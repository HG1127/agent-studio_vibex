此流程用于独立 Agent Studio 的全新、空 PostgreSQL 18 数据库。旧数据已被
确认为可丢弃的测试数据，因此不导入 SQLite 数据、旧账号、旧任务或历史归档。
当前 PocketBase 运行环境不切换；正式迁移仍为 **NO-GO**。
048人工回复已验收；049/050记忆在baec3f2通过可选结构的真实PG18/HTTPS/mTLS及主浏览器14项执行场景。当前新增的是全新050默认顺序候选，离线计划已核对，整库事务/权限/PG18/浏览器回归仍待本候选CI；真实目标尚未初始化或切换。

## 默认只读审查

入口是 `services/pg-api/src/baota-pg18-runtime-init.mjs`。默认没有执行动作；
使用 `--plan` 只读取版本化源代码并输出顺序、源摘要、目标和保持禁用的结果。
无需读取密码文件、安装依赖或建立数据库连接。

```text
node services/pg-api/src/baota-pg18-runtime-init.mjs --plan
```

审查包只含源代码、SQL、依赖声明、文件摘要和本说明。解压后先校验文件摘要，
再运行上述离线计划。计划中的 `source_sha256` 对应该份 SQL 快照；执行需要
提供相同摘要，不能把另一份计划的确认值套用到改变后的源文件。

## 受控执行条件与结果

代码准备不表示允许在目标主机执行。目标执行仍需要具体主机、备份和管理员
授权。执行入口只接受 `--execute --confirm-empty-database agent_studio
--expected-source-sha256 <审查后的摘要>`，并要求以下所有条件：

- Linux、PostgreSQL 18、pgvector 0.8.7、`127.0.0.1:5333/agent_studio`，实际管理员为 `postgres`。
- 原基础初始化开关 `AGENT_STUDIO_BAOTA_FRESH_PG_ENABLED=true`，精确目标环境字段，
  以及独立标记 `AGENT_STUDIO_PG18_RUNTIME_INIT_APPROVED=APPROVE_EMPTY_PG18_RUNTIME_INIT_ONLY`。
- 管理员、API 和 Worker 三个独立的外部密码文件；保留原有私有权限、非符号链接、
  文件与密码独立性及新服务密码强度检查。禁止环境中混入 `DATABASE_URL` 或 `PG*` 连接配置。
- 已创建的数据库为空，应用结构、数据和初始角色不已存在。此工具不创建或删除数据库，
  不清空既有结构，也不覆盖现有实例；重复执行会拒绝。

整个基础结构、角色、认证、019—050 迁移、权限检查及回执处于同一个数据库事务。
中途失败会回滚新结构、角色和回执，保留原来的空数据库供核查后重试。
这不能替代正式切换后发生故障时的备份恢复。

提交前检查所有预期表、FORCE RLS、空业务表、精确版本序列、角色属性与成员关系、
API/Worker/身份角色对模型和工具密文的拒绝，以及全部知识辅助角色的现有权限审计。
API、Worker 和认证的保留登录角色均保持 **NOLOGIN**，辅助角色也不能登录。
没有启动任何服务、模型调用、外部工具、付费索引、计划任务或对外流量。

初始化不安装操作系统服务、不配网络证书、不创建员工、不激活登录，也不生成或分发
模型/Worker 凭据。后续各服务登录的独立凭据、启用范围及启动仍需单独受控准备和验收。
认证激活预检查已接入完整回执、精确结构、空业务表、禁用角色和辅助权限审计；它不以
“表更多了”作为就绪依据。原 23/22 基础结构路径继续保留。完整路径的受控顺序为：
先完成初始化并核验回执，再单独审查认证登录与 HBA，按既有授权流程激活认证登录，
然后准备首位管理员；API、Worker 和其他 Broker 登录的凭据与启用继续单独审查。
六类服务账号的逐项工具、守卫与事务回执见
[服务账号准备说明](PG18_SERVICE_LOGIN_PREPARATION.md)。该工具不启动服务。
各准备边界使用[完整运行态分阶段只读核验](PG18_RUNTIME_PREPARATION_POSTCHECK.md)，
包含初始化、认证启用、首位管理员和全部服务账号四个状态；旧基础 SQL 检查不适用于完整路径。
认证激活的首轮采集使用 READ ONLY 事务，执行前仍会在原有激活锁内再次核验。
旧的基础初始化器继续只建立基础结构；它的数量检查已修正为当前的 23/22，而完整运行态
应采用此说明和完整入口。较早审查材料中的 20/19 或 21/20 数量不能用于本版本签收。

现有受限 CI 转换器替换；生产 SQL 与目标守卫保持不变。CI 中的服务登录启用发生在
完整初始化成功之后，且仅用于合成数据、Native Cookie、独立登录和私有 mTLS 验证。

目标服务凭据与网络检查、真实员工 UAT、长时间 OS Worker/重启/丢失响应验证、
目标备份恢复和切回演练、管理员签收。任何离线计划、初始化回执或合成 CI 成功都不
自动满足这些条件，也不自动将生产状态改成 GO。
