# Agent Studio V18｜协作式取消与运行控制一致性（2026-10-22）

## 本阶段目标

V17 修复了运行中暂停导致租约失效的问题。本阶段继续修复相邻的“取消任务”路径：取消不能直接改写正在执行的运行状态，否则外部工具可能已完成写入、但其结果或副作用日志尚未持久化。

## 1. 新的协作式取消协议

1. 取消接口在事务内核验任务归属、当前状态与有效执行租约。
2. 若状态为 `running` 且存在有效租约，接口只设置 `checkpoint.cancel_requested=true`，保持运行状态和当前租约不变；前端展示“取消请求中”，禁用重复取消操作。
3. 当前步骤可以完成正在进行的模型/工具调用，并先保存工具结果、检查点和副作用日志。
4. 当前步骤返回后，执行引擎在租约保护下再次读取最新检查点；如果取消标志仍存在，就原子地清除取消/暂停标志和待输入/待审批状态，将任务转为 `cancelled`，且不再启动下一步。
5. 如果一个新 Worker 接手时发现遗留的取消标志，则会在发起新模型或工具调用前完成取消。
6. 若任务已处于等待输入、等待审批、暂停或排队状态，且没有正在执行的步骤，则可以立即取消。待输入和待审批字段会被清空，防止迟到的响应或批准重新唤醒任务。
7. 如果终态已先于取消请求提交，终态不被旧请求覆盖；取消标志会在成功/失败终态路径中清除。外部写操作若返回未知结果，仍保留失败诊断与人工核查要求，不会因取消请求掩盖风险。

## 2. 竞态修复

- 增加通用的租约栅栏状态变更函数 `mutateStatuses`。默认的 `mutate` 仍只允许 `running`，新函数只在调用方显式列出的状态中允许变更，并继续验证租约令牌和员工归属。
- 将 `ask_user` 的等待状态保存改为同一租约保护事务，避免它用过期检查点覆盖并发写入的取消请求。
- 取消请求优先于暂停请求；正在取消的任务拒绝新的暂停请求。
- 取消状态下清理待审批和待输入信息，迟到的审批接口返回冲突，不得把已取消任务改回运行中。

## 3. 前端体验

运行状态摘要、运行控制栏和运行详情页在取消请求挂起时统一展示“取消请求中”，说明当前步骤会先安全收尾、保存检查点，然后取消后续执行。重复取消被禁用，避免用户因状态暂未切换而反复点击。暂停按钮也会在取消请求挂起时禁用。

## 5. 仍需遵守的边界

协作式取消不会强行中断已经发出的第三方 HTTP 请求，也不承诺撤销外部系统已经发生的操作。它保证当前步骤在安全边界保存结果，之后不再启动新步骤。外部响应丢失或结果不确定时，仍必须走现有的人工核查流程。
