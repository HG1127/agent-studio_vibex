# 电脑连接器首次绑定与恢复（2026-10-28）

## 当前入口

- 工作台：工具与连接 → 执行资源中心 → 我的电脑 → 连接电脑与浏览器。
- Windows x64 独立包：`agent-studio-connector-win-x64.zip`，解压后只双击 `Start-Connector.cmd`。
- 连接器版本：`0.1.0-preview.7`，Windows 未签名预览包；需安装 Google Chrome，不需要用户安装 Node.js、pnpm 或项目源码。
- `127.0.0.1:8180` 仅供同一台 Windows 预览机使用，其他员工连接需公司同事可达的 HTTPS 工作台；单机运行不能当作团队部署验收。

## 本轮发现的实际故障

旧版 `desktop.mjs` 在唯一已保存连接自动恢复时，会把 Chrome 目标直接设为旧工作台；新设备的连接文件导入界面被跳过。同时旧版直接以 `windowsHide:true` 的 `spawn` 启动 Chrome 后输出“连接器已启动”，没有确认管理页面已加载。用户看到 CMD 运行、网页却一直等待新设备，是合理且可复现的断点。

## 新版交互

1. 双击唯一的 `Start-Connector.cmd`。
2. 即使旧设备可以自动恢复，也**始终**在前台打开 Chrome 专用的本机连接窗口；自动恢复旧连接不会替代新设备绑定。
3. 本机窗口首先显示「连接新账号或设备」，选择刚下载的 **JSON 连接文件**、核对服务器、用途及允许网站，选择具体文件/文件夹，勾选确认，点击「确认连接并启动」。
4. 浏览器打开使用不隐藏的 Chrome 专用窗口（`--new-window --app=...`），并以本机认证的 `/api/state` 响应判断 UI 实际就绪；如未就绪再尝试 Chrome 普通窗口。即使两次都失败，CMD 会明确显示“窗口未打开，不代表配对成功”。
5. 新设备只有在服务端确认配对、真实心跳和能力清单就绪后，网页显示「已在线」。CMD 的启动信息不能代替服务器验收。
6. 已保存设备仍可直接恢复，保留原凭据与权限，后续日常授权管理在工作台页面内完成。

## 过期与故障恢复

- 首次启动和文件导入耗时可能超过连接文件的五分钟有效期；请在启动器可用后生成连接文件。过期时只对同一条**尚未配对**的设备更新连接文件，不另外生成同名设备，不重配已绑定设备。
- 若 CMD 提示浏览器窗口未就绪，先在 Chrome 窗口/任务栏查找本机设置，再核实 Chrome 安装或系统终端管理策略。切勿因为 CMD 未显示错误就认为新设备已经上线。
- 本机授权最终确认只能由用户亲自完成，不由网页静默批准；不要转发连接 JSON 或上传本机设备凭据。
- 本轮不撤销旧设备、不修改已有本机授权、不重建预览数据库、不推送部署生产。

## 开发验收

- `node --test tests/connector-startup.test.mjs tests/connector-distribution.test.mjs`：验证唯一旧设备仍显示本机新连接入口、多旧设备/无旧设备、Chrome 双路径恢复及认证状态回执。
- `node tests/connector-manager.chrome.mjs`：隔离后端、真实 Chrome、实际文件读写与配对；首次连接、停止/恢复、错误文件、取消和布局验证。
- `pnpm connector:build && pnpm connector:test-package`：打包及独立运行环境真实烟雾测试。
- `pnpm check`、`pnpm test:e2e:parallel`：最终全项目回归。原生 Windows 文件/确认窗口仍应在实际员工电脑做人工验收；自动化适配器不等于人工确认。
