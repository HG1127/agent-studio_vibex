# Agent Studio V17｜协作式暂停与安全续跑（2026-10-22）

## 本阶段目标

在上一轮 Agent 创建向导与执行连接页体验改进基础上，修复运行中点击“暂停”时，任务状态与正在执行的步骤互相冲突的问题。目标不是让暂停按钮更快地改变状态，而是确保外部动作的结果、检查点和执行租约一致。

## 1. 已识别的缺陷

原暂停接口在任何运行中的状态下都会立即把 `agent_runs.status` 写成 `paused`，并将检查点的 `claim_until` 清零。

如果模型请求或外部工具调用仍在执行，后续的执行租约保护要求运行状态保持 `running`。提前改为 `paused` 可能使当前步骤无法提交结果；若外部写入已成功但结果没有落库，则后续恢复可能面对不确定的外部副作用。

## 2. 新的协作式暂停协议

1. 暂停接口在数据库事务中检查当前员工归属、运行状态与有效的 Agent 执行租约。
2. **存在有效执行租约：** 不改变 `running` 状态，不撤销当前租约；只在检查点写入 `pause_requested=true`，并向界面返回“当前步骤正在收尾”。
3. 当前步骤继续按现有执行保护完成工具调用、记录副作用结果，并提交检查点。检查点保存会合并最新持久化状态，因此保留暂停请求。
4. 当前步骤释放租约后，下一次调度先重新核验暂停标志；若标志仍存在，则在执行任何新步骤前原子地清除标志并切换为 `paused`，随后返回，不再调用模型或工具。
5. **不存在有效执行租约：** 运行没有正在进行的步骤，可以立即切换为 `paused` 并清除旧暂停标志。
6. 成功或失败终态优先于未完成的暂停请求；终态保存会清除 `pause_requested`，避免历史标志污染后续状态。

运行详情、运行状态摘要和控制栏都会在 `running + pause_requested` 时展示“暂停请求中”，禁用重复暂停操作，并明确说明当前步骤会先收尾。等待用户输入或审批时，界面保留真正的等待状态，并附加暂停请求提示；如果暂停请求仍有效，用户完成输入/审批后，调度会在下一步执行前应用暂停。

## 4. 边界

这项修改不会中止已经发出的 HTTP 请求，也不会宣称外部系统可被回滚。它保证的是：不以“立即改变状态”的方式破坏当前步骤的检查点；当前步骤完成后暂停后续步骤。若外部系统响应丢失或结果不确定，仍须遵守现有副作用核查流程。
