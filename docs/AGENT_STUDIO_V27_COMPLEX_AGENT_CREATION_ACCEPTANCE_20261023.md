## 1. 用户目标与判断标准

V27 不再优先扩展 Worker 底层功能，转而检验：用户只需描述一项复杂任务，系统能否识别真正的执行角色、工具能力、可核验交付物；员工确认后能否配置并启动 Agent，执行真实工具、跨角色传递结果、经人工批准处理写操作，最终提交可阅读且具证据链的交付物。

必须分开三个不同层次：

1. **创建链路有效性**：自然语言进入模型设计器，结构化产生角色依赖、能力需求、任务步骤和完成标准，真实数据库持久化。
2. **执行链路有效性**：真实 PocketBase Worker 与实际本地 Chromium/PDF/XLSX 工具协作，持久化角色交接、工具执行结果与人工审批，实际导出并重新读取文件。
3. **认知质量与生产可用性**：真实通用模型是否能稳定规划未知任务、核验来源可靠性、处理模糊决策和真实 SaaS 权限。这不能由固定模型测试或本地 fixture 证明，本轮不得宣称通过。

## 2. 已识别并修改的两处产品缺口

### A. 结构化能力规划误混入执行权限

原创建流程将模型提出但未匹配到可执行连接的 `PDF提取`、`邮件发送` 等人类可读别名，直接放入 `spec.tools`，使“尚缺工具”的规划信息污染全局可执行工具清单。对于多角色 Agent，既可能妨碍启动预检，又使用户误以为工具已就绪。

新行为：当模型返回非空结构化 `capability_requirements`，只把真实存在且由当前账号许可的匹配工具放进初始工具清单；未匹配能力仍在 Harness 规划卡中显示，要求员工选择连接、分配负责角色并保存。不得由模型自动赋予 `send_email` 写权限。**旧版没有结构化需求的 Agent 继续保留原有差距别名兼容行为**，无需破坏历史草稿。

### B. “运行成功”不等于复杂 Agent 真的完成

原创建向导依据保存版本快照、成功状态和可选文本断言决定是否允许进入发布。一个五角色方案即使遗漏部分角色交接或没真正执行必需工具，也可能产生看似完整的最终结果而被误判“已具备发布前提”。

新增 `evaluateComplexAgentAcceptance`：当保存方案有 2 个或以上角色时，读取本人真实运行 `/api/agent-runs/{id}/detail` 返回的 checkpoint + event 证据，校验：

- 角色依赖的实际完成顺序与当前冻结方案一致；
- 每个角色有非空持久化成果和对应角色完成事件；
- 每项必需的可执行工具能力在正确责任角色下出现匹配的 `tool_call + tool_result`；
- 写操作存在同一工具、同一步骤的 `approval: approve` 事件；
- 最终成功状态和非空结果存在，并与本次保存快照匹配。

新向导显示“已核验角色 x/y，必需工具能力 x/y”；如有遗漏，就明确指出角色、能力、审批证据缺口并阻断发布。既有单 Agent 任务不受这一新增多角色门槛影响。

**局限：** 这是可审核的**流程执行结构性证据**，不是对模型观点的事实真伪、工具返回数据或金融分析正确性的终极证明。最终仍需业务核验。

## 3. 核心复杂任务验收场景

使用隔离任务“发行人多源研究、交叉复核与审批交付”：

- **网页研究**：Chromium 打开仅允许的本地网页，读取来源；
- **PDF 核查**：解析真实生成的 PDF、页码与附注；
- **Excel 分析**：读取真实 `.xlsx` 的单元格 A2=120 与 B4=30，计算得到 90；
- **独立审核**：交叉核对来源并说明风险；
- **审批后交付**：只有收到人工许可后，使用受控本地写工具导出可重新读取的报告，模拟邮件只写入本地 fixture，不向真实收件人发送。

创建阶段使用固定、结构化的设计模型 fixture 驱动真实 Chrome 页面和 PocketBase API，检查输出角色、能力、数据库持久化以及“模型建议不等于授权”。运行阶段使用确定性策略模型驱动真实本地 Chromium/PDF/XLSX/市场工具调用，保留真实执行、审批及审计记录。

验收还包含各种失败注入：模型给出最终答案但缺少角色或工具证据、审批不属于同一步、假工具 ID、不完整依赖角色、非授权写操作、隔离环境断网、历史成功版本与当前保存版本不匹配，以上应阻断上线。

## 4.1 服务端正式版本门槛

通过 `pocketbase/pb_hooks/modules/harness_complex_release.js` 与版本 API 校验，复杂 Agent 不得只凭成功输出或客户端布尔值发布。服务端必须核对正式验收来源、冻结快照、角色交接、工具调用结果、同一步骤的审批与配置的质量断言。

- 未经正式验收的复杂版本：服务器返回 409，不能发布；
- 五角色正式验收完成且证据齐全的版本：真实隔离 PocketBase 已验证可以发布；
- 单助手历史发布流程：保留兼容行为；
- 版本测试预算按角色数有界扩展，避免固定 8 步误判复杂任务不合格。

该门槛是工程执行证据而非业务事实真伪认证。

## 5. 产品结论与生产边界

**不能把固定模型的本地测试结果等同于真实模型自主规划未知业务任务的成功率。** 本阶段主要证明“创建产品完整工作流”及“实际工具执行与审批控制”的可行性；真实 API/插件权限覆盖、模型推理质量、来源真实性与适用范围，需要用真实授权模型和多任务的人工独立评分进一步验证。生产仍为 **NO-GO**。
