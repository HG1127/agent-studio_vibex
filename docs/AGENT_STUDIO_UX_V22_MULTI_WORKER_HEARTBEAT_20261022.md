# Agent Studio V22｜多 Worker 独立心跳、恢复诊断与安全接管

日期：2026-10-22  
开发分支：`feat/harness-design-workspace-20261021`  
发布状态：**仅开发工作区，未提交、推送或部署**

## 1. 修复的问题

此前不同 Worker 实例都往 `agent_worker_health.worker_name=main` 写入心跳、执行次数和子系统状态。多个实例并发时，单行记录互相覆盖；仪表盘只能知道最近“有人上报”，无法分辨哪个进程最近活跃。

## 2. 独立实例与长时间执行心跳

`worker/run.mjs` 在**每次进程启动**时生成随机的 `w-<24位十六进制>` 实例 ID。此 ID 不含主机名称、员工、授权信息或 API key；新进程（包括自动重启后的进程）使用新 ID。每次推进队列时，将 ID 与经过限制的定时调度/知识索引状态一同上报。

新增 `POST /api/internal/worker/heartbeat`：

- 强制验证与原 Worker 一致的服务端 Token；
- 只接受 `main`（向后兼容旧调用）或严格格式的随机实例 ID；
- 最小化更新该实例 `agent_worker_health.last_seen`；
- 不接受租约令牌、用户标识、原始错误堆栈、回调 URL 或执行目标；
- **不能**认领、续租、取消、恢复或修改任何 Agent / Workflow 的任务执行租约。

独立 Worker 进程每 30 秒（可配置 `AGENT_STUDIO_WORKER_HEARTBEAT_INTERVAL_MS`，允许 1–60 秒）通过独立 HTTP 请求上报。即使 Worker 主循环在等待一个较长的模型或工具请求，也可继续报告进程的最近活动；失败的心跳记录有限日志，不将其解释为执行结果成功。Worker 被禁用或认证失效时仍按原安全策略停机。

已有 `agent_worker_health` 记录不丢失，旧版无实例 ID 的 Worker 保留 `main` 路径。更新已执行步骤计数时先在事务内读取最新记录，避免覆盖单独心跳已经写入的较新时间。

## 3. 控制台展示与恢复诊断

`GET /api/worker/status` 改用最近更新时间查询**最多 33 条实例记录**，前端只展示最近 12 个实例，并明确提示截断。返回的是随机别名、心跳相对时间、最后步骤时间及执行尝试数，不暴露其他员工的任务 ID。

工作台可折叠“Worker 实例”详情，显示各实例近期是否上报。**近期心跳不等于进程当前在线，也不等于它持有某个任务的租约**。

用户专属队列还新增两项指标：

- `expired_lease_candidates`：属于当前员工且任务仍为 running、租约已过期的候选数量。它们需要由新的 Worker 重新原子领取并验证检查点，**不代表可无条件安全重放**。
- `unresolved_writes`：当前员工 `started` 或 `unknown` 的外部写意图数，包含尚未超过 10 分钟的记录。它们不能在未经核查的情况下直接再次执行。

这些信息只经服务端按已验证员工归属聚合查询，不把别人的 run_id 或副作用参数透传给前端。旧版 `needs_review` 仍按现有超时策略提供人工核查计数。

## 5. 刻意没有实施的高风险操作

本轮实现的是**Worker 进程保活观测**，**不是**“执行租约后台自动续租”。现有 CAS 租约依然只由持有合法租约 Token 的执行器在操作边界续期，超长单次阻塞调用超过有效租期时，旧执行器必须被拒绝提交结果。不能让任何只拥有 Worker Token 的普通心跳请求去延长任意任务的租约，否则会掩盖崩溃、破坏栅栏和安全接管。

未来如要实现长步骤执行期间的租约连续续期，应引入与执行 Token 加密绑定的独立续租代理、主动中断/租约所有者切换检测、跨进程故障注入和业务级幂等审计，先在隔离环境验证后再讨论生产部署。

实例状态列表不是跨机器完整的调度拓扑；本次未实现对某个工作中任务与持租约 Worker 的强绑定展示，也未实测生产网络长期分区。生产环境仍是 **NO-GO**。
