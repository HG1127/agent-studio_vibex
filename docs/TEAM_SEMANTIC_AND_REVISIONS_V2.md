# Agent Studio V2：团队语义检索与 Agent 安全版本恢复

日期：2026-10-15。项目：`agent_studio_vibex版本` 独立部署源码。仅隔离环境开发与测试，**生产状态 NO-GO**。

## 一、团队知识库语义检索

### 1. 授权规则

- 所有者共享知识库时，可授予员工 `Viewer` 或 `Editor` 文档权限，**共享语义权限独立开关且默认为关闭**。
- 所有者可在「知识库 → 团队知识库授权」为单个员工启用或关闭语义能力。权限由后端 `knowledge_acl.js` 校验，任何人不得凭知识库 ID 或前端页面状态直接查询。
- 仅当 **所有者已有文档向量索引**、所有者已授予当前员工语义权限、当前员工拥有自己的 Embedding 模型连接，并且双方**模型 ID 和经过服务器白名单验证的模型服务 Base URL 完全一致**时，允许使用共享文档向量。
- 所有者的原文及向量留在其所有权数据表。查询者调用自己的 Embedding API **只发送查询词，不发送所有者全部文档**，费用由查询者所配置的模型连接承担；所有者已经发生的文档向量化费用仍归原所有者。
- 提供商实际服务模型若暗中更新，即使 URL、模型 ID 相同也可能使语义效果发生漂移；当前通过模型信息一致性和向量维度校验降低风险，**尚未实施供应商模型版本哈希签名**。
- 授权被撤销、用户禁用、模型删除/切换或知识库删除，服务端会拒绝后续访问。慢速模型查询结束后重新校验权限，并在返回检索片段前再做一次安全核验。
- 默认 `auto` 优先将兼容的共享库纳入混合检索；某共享库未开通或不兼容时，对该库回退为关键词检索。指定 `semantic`、`hybrid` 时，存在未授权/不兼容的选定共享库将得到显式 409，**不伪装为语义结果**。

### 2. 页面及执行链路

- 所有者：在 `/knowledge-bases` 的「团队知识库授权」配置成员和「语义检索」独立开关，可撤回。
- 查看者/编辑者：同一知识库页面新增「团队语义检索」状态，显示无授权、本人模型未配置、模型不兼容、索引未完成/部分/就绪等诊断。
- 统一 `knowledge_search` 后端由 REST、Agent 和 Workflow 使用。测试验证近义改写问题可以召回原先只靠关键词未匹配的原文，并返回 `[文件名 · 片段N]`。
- 已有后台 Worker **只为原所有者**索引文档，成员复用这些向量，并不会为每位 Viewer/Editor 生成完整文档副本。
- 新增增量迁移 `knowledge_0006_shared_semantic_consent`：给原授权记录增加 `semantic_allowed INTEGER NOT NULL DEFAULT 0`，历史共享成员不会被自动赋予语义授权。
- 新增 `GET /api/knowledge-bases/semantic/shared-status?base_id=...`，仅返回当前员工有权访问的本库状态与索引片段统计，不暴露所有者 Provider 地址、账户 ID 或 API Key。

### 3. 安全和成本限制

- Embedding 新文档时，原文片段仍会发送给所有者批准的向量服务商；查询者的向量服务商只接收查询文本。Agent 最终答案生成可能会将匹配片段发送至**查询者自己的 LLM**；应履行公司资料分级和服务商合规审批。
- 除具体成员的许可外，当前还没有团队部门动态 ACL、统一成本中心、用量预算预警、内容分级/脱敏、完整的 pgvector/ANN 及大规模索引性能验证。
- Goja/SQLite 仍使用有界线性向量扫描，单库语义最多最近 700 片段；关键词最多约 1600 候选。**不能宣称全量召回保证**。

## 二、Agent 协作版本差异与安全恢复

- `/agent-collaboration` 新增**逐字段差异对比**（目标、任务范围、交付物、任务计划、完成标准）。
- Agent 所有者采纳协作提案时，同一 SQLite 事务内自动记录 `before_accept`、`accepted` 两份**安全文本快照**；模型 Key、工具权限、知识库绑定、实际执行数据不会复制进版本表。
- 所有者可打开「Agent 描述与规划版本」查看历史，选择版本、填写恢复理由并确认。恢复前必须提供与当前**完整** Agent 配置匹配的版本指纹；不匹配返回 409。
- 恢复仅覆盖上述五个描述/规划字段，不重置模型、工具、知识库等受保护字段。恢复前后均增加新快照 `before_restore`、`restored`，并写入原操作审计。
- 所有待审核的旧提案会在恢复时作废，防止因回到旧文本内容而恢复意外有效的草稿。
- 版本查看/恢复接口均仅限所有者。Editor 和 Viewer 没有查看历史快照及恢复权限。
- **Owner 直接编辑也记录安全版本：** 原 `/api/agent_specs/{id}` 的方案更新现使用同一 SQLite 事务保存修改前/后的安全文本快照，并立即作废此前 Pending 的旧协作草稿。可选 `expected_current_hash` 实现乐观版本校验；不填写仍支持既有客户端。单纯改名不会生成重复的描述版本。
- **范围边界：** 历史仍只保存上述五项描述/规划字段，不记录工具或模型凭据的完整 JSON。Agent 创建、删除、直接修改名称、执行时检查点与日志不属于此描述历史；正式的全字段 Git 式版本恢复仍未实现。

相关服务：`modules/agent_collab_history.js`、`agent_collab_versions.pb.js`、`agent_specs.pb.js`；数据库 `agent_studio_spec_revisions` 新增可向后兼容的 `entry_type` 来源字段，用于区分协作审核和所有者直接更新，仍不触及现有敏感配置数据结构。

## 三、自动化验收与上线限制

```sh
pnpm test:team-knowledge       # 多员工共享近义召回、双方模型与权限、费用归属、Agent/Workflow、撤权
pnpm test:agent-collaboration # 提案审核、并发冲突、历史版本、受控恢复、未审核草稿作废
pnpm test:migrations          # 旧知识库与授权的增量迁移，默认语义授权为否
pnpm test:e2e                # 完整业务回归
pnpm check                   # 单元、类型、前端生产构建
```

以上测试使用独立临时 PocketBase/SQLite 和**本地模拟的模型服务**。正式上线前仍须完成：真实公司网关/HTTPS、员工身份与权限 UAT、模型服务与成本签收、服务端 Worker 24 小时常驻观察、数据备份与恢复、原 RH 账号到独立账号的经授权映射、公司服务器数据库迁移审查。

**绝不在本轮自动部署、切换 PostgreSQL 或写入正式库。**
